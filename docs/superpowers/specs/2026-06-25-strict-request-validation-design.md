# Строгая явная валидация входных данных заявки

Дата: 2026-06-25
Ветка: `feat/strict-request-validation`

## Контекст и проблема

Модель `ApplicationRequest` в `server.py` принимает `birth_date: date` и
`country: str`. Сейчас «дата только в формате `ГГГГ-ММ-ДД`» обеспечивается
**неявно** — самим парсером типа `date` в Pydantic. Это поведение зависит от
версии Pydantic (в старых версиях `date` принимал, например, число-timestamp) и
выдаёт техническую англоязычную ошибку. Строгость нигде не закреплена нашим
кодом и нашими тестами.

Задача — сделать строгость **явной** и **защищённой тестами**, не меняя контракт
API (валидные запросы продолжают работать как раньше).

## Цель

- Собственный валидатор `birth_date`, принимающий дату строго в формате
  `ГГГГ-ММ-ДД`, с понятными сообщениями об ошибках на русском, не зависящий от
  версии Pydantic.
- Сохранить совместимость с внутренним Python-кодом и тестами, которые передают
  готовый объект `date`.
- Явно зафиксировать тестами, что `country` — обязательная непустая строка (не
  число и не другой тип).

## Не-цель (YAGNI)

- НЕ ограничиваем страну списком допустимых значений (Enum) — это отдельная
  задача.
- НЕ добавляем `extra="forbid"`, валидацию формата телефона и прочие новые
  правила — контракт API не расширяем.
- НЕ трогаем бизнес-логику `make_decision`, возрастные правила, стоп-лист стран.

## Поведение валидатора `birth_date`

| Вход | Результат |
|------|-----------|
| `"2000-05-15"` — строка строго `ГГГГ-ММ-ДД` | принять → `date(2000, 5, 15)` |
| `date(2000, 5, 15)` — объект `date` | принять как есть |
| `"15.05.2000"`, `"2000/05/15"`, `"2000-5-5"` | отклонить: «Дата должна быть в формате ГГГГ-ММ-ДД (например, 2000-05-15)» |
| `"2000-13-40"` — формат верный, даты не существует | отклонить: «Несуществующая дата (проверьте месяц и день)» |
| `1000000`, `20000515` — число/timestamp | отклонить: «Дата должна быть строкой в формате ГГГГ-ММ-ДД» |
| `"2000-05-15T10:00:00"` — дата со временем | отклонить (не соответствует формату) |
| `datetime(2000, 5, 15, 10, 0)` — объект `datetime` | отклонить (это не чистая дата) |
| дата в будущем | отклонить существующей проверкой `birth_date_not_future` |

## Изменения в коде (`server.py`)

1. Добавить `import re`.
2. Добавить в `ApplicationRequest` валидатор перед существующим
   `birth_date_not_future`:

   ```python
   @field_validator("birth_date", mode="before")
   @classmethod
   def parse_strict_birth_date(cls, v: object) -> date:
       # Уже чистый date (но не datetime) — принимаем как есть.
       if isinstance(v, date) and not isinstance(v, datetime):
           return v
       if not isinstance(v, str):
           raise ValueError("Дата должна быть строкой в формате ГГГГ-ММ-ДД")
       s = v.strip()
       if not re.fullmatch(r"\d{4}-\d{2}-\d{2}", s):
           raise ValueError(
               "Дата должна быть в формате ГГГГ-ММ-ДД (например, 2000-05-15)"
           )
       try:
           return datetime.strptime(s, "%Y-%m-%d").date()
       except ValueError:
           raise ValueError("Несуществующая дата (проверьте месяц и день)")
   ```

3. Существующий `@field_validator("birth_date", mode="after")`
   (`birth_date_not_future`) остаётся без изменений — `before` отдаёт ему
   корректный `date`.
4. Поле `country` и валидатор `strip_and_require_nonempty` не меняются.

## Тесты модели (`tests/test_decision.py`)

Добавить:

- параметризованный тест плохих форматов даты → каждый `raises`:
  `"15.05.2000"`, `"2000/05/15"`, `"2000-5-5"`, `1000000`, `20000515`,
  `"2000-05-15T10:00:00"`;
- тест несуществующей даты `"2000-13-40"` → `raises`;
- тест-регрессия: `birth_date=date(2000, 5, 15)` (объект) принимается и
  `req.birth_date == date(2000, 5, 15)`;
- тест: `country=123` (не строка) → `raises`.

Существующий `test_request_birth_date_bad_format` оставляем (он становится
частным случаем нового набора).

## Тесты HTTP-ручки (`tests/test_http.py`)

На уровне эндпоинта `POST /applications` (через `TestClient`), в стиле
существующего `test_application_validation_error`:

- **невалидный запрос → ручка отдаёт ошибку**: `_adult_payload()` с подменённой
  датой `"15.05.2000"` → статус `422`; в `body["detail"]` присутствует ошибка
  по полю `birth_date` (`"birth_date" in [e["loc"][-1] for e in detail]`).
- **валидный запрос → ошибки нет**: `_adult_payload()` с корректной датой
  `"2000-05-15"` (поле `birth_date`, по которому добавлена строгая валидация) →
  статус `200`, тело содержит решение (`status`, `applicant`). Это позитивная
  пара к тесту выше; «новое поле» здесь = строго провалидированная дата.

## Критерии готовности

- `pytest` зелёный целиком (новые тесты + все существующие, включая
  `_valid_decision_request`, передающий объект `date`).
- Валидные запросы из `model_config` example и из тестов работают как раньше.
- Сообщения об ошибках валидации — на русском.
