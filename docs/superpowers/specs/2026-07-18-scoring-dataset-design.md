# Analytics store `scoring_dataset` — дизайн

- **Дата:** 2026-07-18
- **Статус:** дизайн согласован (Екатерина, 2026-07-18)
- **Автор:** Екатерина (+ Claude)
- **Связан с:** [партиционирование ради retention](2026-07-15-partitioning-retention-design.md) —
  **пререквизит** к нему: без постоянного слепка ретеншен сотрёт обучающие данные скоринга.

## 1. Зачем (бизнес-цель)

Операционные таблицы уходят под **агрессивный ретеншен** ради места (`esc` 7 дн, `applications`/`loans`
чистятся раз в месяц). Но скорингу и аналитике возврата нужна **история**: чтобы обучать скоркарту и
считать «долю потерь», надо на вызревших займах связать **BKI-фичи** (на момент решения) с **исходом**
(вернул/не вернул). При этих сроках данные не совпадут во времени:

```
BKI-фичи в esc → живут 7 дн
исход в loans  → жил бы 30 дн
заём вызревает → на 60-й день (канон дефолта)
```

→ ни у одного вызревшего займа не будет одновременно и фич, и исхода. Ретеншен и скоринг воюют.

**Решение:** постоянная компактная таблица `scoring_dataset` — **одна строка на заявку** с фичами,
метаданными и исходом. Наполняется до чистки операционных таблиц; дальше `esc`/`applications`/`loans`
чистятся свободно, а история для обучения живёт. Это **не возврат витрины** `bki_reports` (та была
разовой копией и удалена из-за диска) — это **постоянный накопитель** без сырого XML, поэтому маленький.

## 2. Scope

**В scope:** таблица `scoring_dataset`, вьюха-разметка `scoring_dataset_labeled`, ежедневная
`pg_cron`-джоба наполнения, ревизия сроков ретеншена (`loans` 30 → ≥65 дн).

**Вне scope:** само партиционирование `esc`/`loans`/`applications` (отдельные планы, идут ПОСЛЕ этой
фичи); построение скоркарты (WOE+логрег — потом, поверх этого датасета).

## 3. Ключевые решения

1. **Наполнение — ежедневная `pg_cron`-джоба** (не запись из приложения). Развязывает операционку и
   аналитику, всё в БД (как `pg_partman`/`pg_cron`), приложение не трогаем.
2. **Охват — ВСЕ заявки v2** (не только одобренные): фичи есть у всех с БКИ, исход — у тех, где выдан
   заём. Даёт и обучение (одобренные с исходом), и reject-анализ (отклонённые с фичами).
3. **Метка bad/good — во вьюхе, не колонкой.** Логика канона в одном месте, считается на текущую дату
   → не устаревает (незрелые сегодня станут зрелыми завтра сами).
4. **`loans` ретеншен 30 → ≥65 дн.** Иначе джоба не увидит вызревший 60-дневный исход до чистки; метка
   завышала бы дефолт (поздний возврат = bad). `applications` 30 дн и `esc` 7 дн — остаются
   (метаданные и фичи джоба снимает рано).
5. **Порядок джоб `pg_cron`:** snapshot → **потом** retention (`run_maintenance_proc`). Слепок раньше
   чистки, иначе гонка на удаление.
6. **Идемпотентность:** upsert `ON CONFLICT (application_id) DO UPDATE`. Джобу можно гонять хоть каждый
   день (и повторно) без дублей.

## 4. Устройство

### 4.1 Таблица `scoring_dataset` (постоянная, без ретеншена)
Одна строка на `application_id` (PK). Группы колонок:

| Группа | Поля |
|---|---|
| ключ | `application_id uuid PK` |
| заявка (на момент решения) | `received_at`, `age int`, `region`, `amount`, `loan_purpose`, `decision` |
| BKI-фичи | `bki_status, score, n_contracts, has_writeoff, has_current_delinquency, overdue_amount, debt_load, max_dpd, n_late, inq_30, inq_90, inq_365` |
| исход | `issued_at`, `loan_amount`, `repaid_at`, `loan_status` |
| служебное | `updated_at` (когда джоба тронула строку) |

- `age` — из `users.birth_date` на `received_at` (users — постоянная dimension-таблица, не чистится).
- `region` ⚠️ — держим для анализа, но в модель осторожно (риск прокси-дискриминации; проверять
  прирост поверх `score`).
- Исходные поля (`issued_at`/`repaid_at`/`loan_status`) храним **сырыми** — метку считает вьюха.

### 4.2 Вьюха `scoring_dataset_labeled` (метка по канону)
Поверх таблицы добавляет:
- `is_mature` — зрелость: `loan_status IN ('вернули','не вернули')` ИЛИ (`выдано` И `issued_at ≤ now - 60d`);
- `is_bad` — только для зрелых: `loan_status = 'не вернули'` ИЛИ (`выдано` И `issued_at ≤ now - 60d`) → bad;
  `вернули` → good; незрелые (`выдано` <60 дн) — `is_mature=false`, из обучения исключаются.
- `ошибка`/техбрак — `is_mature=false` (в знаменатель PD не идут).

## 5. Наполнение — джоба (2 фазы, идемпотентный upsert)

Ежедневно (`cron.schedule`), одной процедурой:

- **Фаза 1 — фичи + заявка.** По заявкам за окно (последние ~30 дн, пока живы `applications`):
  `INSERT ... SELECT` из `applications` (метаданные) + `users` (`age`) + журнала `external_service_calls`
  (`service='bki'`, BKI-фичи из `payload` — тот же разбор, что во view `bki_features_live`:
  скаляры + агрегаты по договорам). `ON CONFLICT (application_id) DO UPDATE` фич/метаданных.
- **Фаза 2 — исход.** По займам за окно (последние ~65 дн, пока живы `loans`):
  `UPDATE scoring_dataset SET issued_at/loan_amount/repaid_at/loan_status FROM loans WHERE application_id = …`.

Окна с запасом перекрывают ретеншен-сроки → ни одна строка не «протухнет» между прогонами.

## 6. Ревизия ретеншена (следствие §3.4)

```
esc             → 7 дн     (фичи джоба снимает за 7 дн)
applications    → 30 дн    (метаданные сняты рано)
loans           → ≥65 дн   (было 30 — иначе не увидим вызревший 60-дн исход)
scoring_dataset → ПОСТОЯННО (это и есть история; маленький, без XML)
```
Это надо отразить в плане партиционирования `loans` (там взять `retention = '65 days'`, не 30).

## 7. Порядок внутри трека

```
scoring_dataset (эта фича, ПЕРВОЙ) → esc → партиции 7 дн → loans → ≥65 дн → applications → 30 дн (после #52)
```
`scoring_dataset` — обязательно **до** включения любого ретеншена, иначе первый прогон чистки начнёт
терять данные.

## 8. Тестирование (blackbox, «сценарий словами → код»)

1. **Фичи и метаданные снимаются.** После прогона джобы в `scoring_dataset` есть строка новой заявки:
   BKI-фичи (score/inq/агрегаты) и метаданные (received_at/region/amount/decision) совпадают с источником.
2. **Исход дописывается.** После выдачи и `/repay` следующий прогон проставляет `repaid_at/loan_status`.
3. **Строка переживает чистку.** После удаления строки из операционной `loans`/`applications` строка в
   `scoring_dataset` цела (данные не потеряны).
4. **Разметка верна.** Вьюха: `вернули`→good; `выдано` ≥60 дн→bad; `выдано` <60 дн→`is_mature=false`.
5. **Идемпотентность.** Повторный прогон джобы не плодит дублей и не ломает существующие строки.

## 9. Риски и оговорки

- **Джоба не отработала N дней подряд** → окна (30/65 дн) с запасом переживают несколько пропусков;
  один пропущенный прогон не теряет данные.
- **Selection bias сохраняется** (видим исход только у одобренных) — это свойство данных, не store;
  отклонённые лежат с фичами без исхода (для reject-анализа).
- **Дубль логики разбора БКИ** (SQL в джобе vs `bki_parse.py` в приложении) — держать согласованными;
  единый эталон — view `bki_features_live` / запрос из сессии 2026-07-18.
- **`pg_cron` порядок** — snapshot должен идти строго раньше retention; если оба на `@daily`, развести
  временем или одной процедурой «snapshot; maintenance».
