# Чёрно-ящичные интеграционные тесты на user story

Дата: 2026-06-29
Ветка: `test/blackbox-integration`

## Цель

Покрыть PetBank интеграционными тестами **методом чёрного ящика**: сервис
поднимается как реальный Docker-стек, тесты стучатся к нему по настоящему HTTP
и проверяют поведение пользовательских сценариев, **ничего не зная о
внутренностях** (не импортируют код приложения, не лезут в БД напрямую).

Тесты пишутся **на user story**. Для каждого теста сначала идёт
человекочитаемое описание сценария по-русски (Дано/Когда/Тогда) в докстринге, и
только потом — код. Описание = контракт того, что тест проверяет.

## Чем это отличается от существующих тестов

В `tests/` уже есть HTTP-тесты, но они «серый ящик»: гоняют ASGI-приложение в
том же процессе (`httpx.ASGITransport`, прямой `import server`) на SQLite. Здесь
же — отдельный процесс/контейнер, реальный Postgres, реальный HTTP, внешний
СтопЛист как отдельный сервис. Это не замена юнит-тестам, а слой поверх них.

## Архитектура стенда

Отдельный docker-compose только для чёрного ящика:
`tests/blackbox/compose.blackbox.yml`. Сервисы:

- **db** — `postgres:16` с фиксированными тестовыми кредами (например
  `petbank/petbank/petbank_test`), порт проброшен на хост для наката миграций.
- **blacklist** — крошечный мок сервиса СтопЛиста. Контракт реального сервиса:
  `GET /check?passport=... -> {"in_terror_list": bool}`. Мок отдаёт `true` для
  заранее известного «плохого» паспорта, иначе `false`. Должен уметь
  имитировать недоступность для сценария fail-closed (см. US-3.14).
  Выбран мок, а не реальный `212.147.238.3:8090` — детерминированно, офлайн,
  без зависимости от чужого стенда.
- **app** — собирается из проектного `Dockerfile` (тестируем текущий код, а не
  образ из ghcr). Env: `DB_*` указывают на `db`, `BLACK_LIST_URL` — на
  `blacklist`. `RATE_LIMIT_RPS`/`REQUEST_TIMEOUT_SECONDS` задаются явно, чтобы
  сквозные сценарии (US-4) были предсказуемы.

### Накат схемы

В Docker-образ кладётся только `app/`; `alembic/` и `alembic.ini` в образ не
попадают, поэтому миграции внутри контейнера не прогнать. Схема накатывается
**с хоста** через `alembic upgrade head` против проброшенного порта Postgres —
это совпадает с реальным проде (миграции применяются вручную, вне образа).

## Обвязка pytest

`tests/blackbox/conftest.py`, фикстура session-scope:

1. `docker compose -f compose.blackbox.yml up --build -d db` → дождаться
   готовности Postgres (polling).
2. С хоста `alembic upgrade head` с `DB_*`, указывающими на `localhost:<порт>`.
3. `docker compose up -d app blacklist` → дождаться `GET /health` == 200
   (polling с таймаутом).
4. Отдать тестам `base_url` (`http://localhost:<порт>`).
5. По завершении — `docker compose down -v` (снести и тома, чтобы данные не
   текли между прогонами).

Клиент в тестах — `httpx.Client`/`requests` по живому `base_url`. Никаких
импортов из `app/src`.

### Маркировка и запуск

Все тесты помечаются `@pytest.mark.blackbox` (регистрируется в
`pyproject.toml`). Запуск: `pytest -m blackbox`. Быстрые юниты по умолчанию идут
без Docker; чёрный ящик запускается отдельно (он медленный и требует Docker).

## Структура тестов

Файлы по user story, в каждом тесте — русский докстринг Дано/Когда/Тогда, потом
код:

- `tests/blackbox/test_us1_applications.py` — подача заявки v1.
- `tests/blackbox/test_us2_loans.py` — жизненный цикл займа.
- `tests/blackbox/test_us3_applications_v2.py` — заявка v2 с проверкой по
  чёрному списку.
- `tests/blackbox/test_us4_ops.py` — эксплуатационные/сквозные сценарии.

## Сценарии (user stories)

### US-1. Подача заявки на кредит (v1) — `POST /applications`
1. Подходящий клиент из РФ (25 лет, сумма указана) → 200, `approved`, причины
   пусты, в ответе ФИО/возраст/телефон.
2. Слишком молодой (16 лет) → 200, `declined`, причина про возраст < 18.
3. Слишком взрослый (40 лет) → 200, `declined`, причина про возраст > 35.
4. Страна из стоп-листа («Китай»), возраст ок → 200, `declined`, причина про
   страну.
5. Несколько причин сразу (16 лет + «Китай») → 200, `declined`, в причинах обе
   проблемы.
6. Кривая заявка (нет обязательного поля / дата в будущем / неверный формат
   даты) → 422 с описанием ошибки (молча не принимается).

### US-2. Жизненный цикл займа — `/loans/{id}`
7. После одобрения с суммой `GET /loans/{id}` → 200: сумма, дата выдачи, статус
   «не отдал», текущая ставка, долг.
8. `POST /loans/{id}/repay` → 200, статус «отдал», долг зафиксирован на дату
   возврата.
9. Повторный `repay` уже отданного → 409.
10. `GET`/`repay` несуществующего займа (случайный uuid) → 404.

### US-3. Заявка v2 с чёрным списком — `POST /applications/v2`
11. Чистый паспорт + возраст ≥ 18 → 200, `approved`.
12. Паспорт в чёрном списке → 200, `declined`, причина про чёрный список.
13. Несовершеннолетний → 200, `declined` (верхней границы возраста у v2 нет —
    взрослым любого возраста можно).
14. СтопЛист недоступен → **fail-closed**: HTTP **200** (не 5xx), `declined`,
    причина «не удалось проверить».

### US-4. Эксплуатационные/сквозные
15. `GET /health` → 200 `{"status":"ok"}`.
16. (опц.) Защита от перегрузки: серия запросов выше лимита → часть получает
    429. Требует низкого `RATE_LIMIT_RPS` в env стенда.
17. (опц.) Долгий запрос обрывается по таймауту. Сложно вызвать в чёрном ящике
    без управляемой задержки на стороне app; кандидат на пропуск/skip, если нет
    надёжного способа спровоцировать.

## Обработка ошибок и краевые случаи

- Если Docker недоступен — фикстура падает с понятным сообщением (или
  `pytest.skip`), а не виснет.
- Готовность сервисов проверяется polling-ом с таймаутом, без «магических»
  `sleep` (кроме разумного шага опроса).
- Уникальность пользователя (`users` UNIQUE по ФИО+ДР+телефон) учитывается:
  тесты, создающие заявки, используют разные ФИО/телефоны, чтобы не ловить
  коллизии между сценариями.

## Что НЕ входит (YAGNI)

- Прогон против реального СтопЛиста и против ghcr-образа.
- Нагрузочное тестирование (только функциональная проверка 429).
- Тесты слоёв БД/логики напрямую — это уже покрыто юнитами.
