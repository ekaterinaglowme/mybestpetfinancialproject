# Дизайн: журнал ответов внешних сервисов `external_service_calls`

**Дата:** 2026-07-14
**Статус:** на согласовании
**Автор:** Екатерина (PetBank)

## 1. Зачем (бизнес-цель)

У PetBank появляется всё больше внешних интеграций: БКИ «КредБюро» (скоринг),
СтопЛист (проверка паспорта), в планах — новые сервисы. Нужен **единый журнал**:
«с кем из внешних сервисов мы общались, что спросили и что нам ответили».

Назначение — история / аудит / отладка / задел под будущие интеграции:
- разобрать инцидент («что реально ответил БКИ по заявке X»);
- увидеть частоту и латентность вызовов (в июле был инцидент из-за медленного БКИ);
- иметь общий приёмник для новых сервисов без новой таблицы под каждый.

## 2. Ключевые решения (из брейншторма 2026-07-14)

1. **Журнал рядом, ничего не ломаем.** Существующая `bki_reports`
   (фичи скоринга + сырой XML) остаётся как есть. Новая таблица — отдельная.
2. **Append-only, каждый вызов — строка.** Ретрай или повторная проверка = новая
   запись; старые не перетираем. Ключ — автономер `id`.
3. **Храним и запрос, и ответ.**
4. **Всё приводим к JSON.** XML от БКИ разбираем в JSON-структуру; JSON от СтопЛиста
   кладём как есть. Единый формат `payload`.
   - Точный XML-оригинал ответа БКИ остаётся в `bki_reports.raw_xml`, поэтому
     дословный юридический след для БКИ не теряется.
5. **`payload` — один JSON-блоб** на паттерне проекта:
   `JSON().with_variant(JSONB(), "postgresql")` (JSONB на проде, JSON в тестах на SQLite).

### Принятые дефолты (рекомендации, не подтверждённые отдельным вопросом — поправь при ревью)
- `id` — **автономер** (BigInteger identity), а не uuid: по нему виден порядок вызовов.
- `application_id` — **nullable** ссылка на заявку: вызов может быть вне контекста заявки.
- `service` — **свободная строка**, без CHECK-ограничения: новый сервис не требует миграции.
- `status` — **свободная строка**, без CHECK: у разных сервисов свои исходы.

## 3. Схема таблицы `external_service_calls`

| Колонка | Тип | Null | Смысл |
|---|---|---|---|
| `id` | BigInteger, PK, autoincrement | нет | порядковый номер записи в журнале |
| `service` | String | нет | `bki` / `stoplist` / имя будущего сервиса |
| `application_id` | Uuid, FK → `applications.application_id` | **да** | по какой заявке звонили (пусто — вне заявки) |
| `called_at` | DateTime(timezone=True), server_default `now()` | нет | когда вызвали |
| `status` | String | да | короткий исход: `ok` / `no_history` / `unavailable` / `error` |
| `http_status` | Integer | да | HTTP-код ответа (200, 403, …) |
| `latency_ms` | Integer | да | сколько миллисекунд отвечал (отлов тормозов) |
| `payload` | JSONB (variant JSON на SQLite) | да | `{"request": {…}, "response": {…}}`, приведённые к JSON |

**Ограничения / индексы:**
- PK: `id`.
- FK: `application_id → applications.application_id` (без каскада; заявки не удаляем).
- Индекс `ix_esc_application_id` по `application_id` — все вызовы по заявке.
- Индекс `ix_esc_service_called_at` по `(service, called_at)` — вызовы сервиса за период.
- GIN-индекс на `payload` **не делаем** сейчас (YAGNI) — добавим, если понадобится
  искать внутри блоба.

### Пример строки (реальный вызов БКИ, приведённый к JSON)

```json
{
  "id": 1,
  "service": "bki",
  "application_id": "3f2b1c4d-…",
  "called_at": "2026-07-14T06:34:48Z",
  "status": "ok",
  "http_status": 200,
  "latency_ms": 1043,
  "payload": {
    "request":  { "Партнер": "PETBANK",
                  "Паспорт": {"Серия": "0000", "Номер": "024949"} },
    "response": { "КодРезультата": 0,
                  "Скоринг": {"Балл": 702},
                  "СведенияОбОбязательствах": {
                    "КоличествоДоговоров": 3, "Договор": [ /* … */ ] } }
  }
}
```

Для СтопЛиста `payload.response` — просто `{"in_terror_list": false}`.

## 4. Приведение к JSON

- **JSON-сервисы (СтопЛист):** тело ответа уже словарь — кладём как есть.
- **XML-сервисы (БКИ):** маленький хелпер `xml_to_dict(element)` в `bki_parse.py`
  (там уже разбор XML БКИ) рекурсивно превращает дерево `ElementTree` в словарь
  (теги → ключи, атрибуты → поля, повторяющиеся узлы → список). Пока XML только
  у БКИ; появится второй XML-сервис — вынесем в общий модуль. Декодирование
  `windows-1251 → str` уже делает
  клиент БКИ (`bki.py`), в `payload` попадает нормальный юникод.
- Возможные потери при XML→JSON (порядок атрибутов, namespace-нюансы) для журнала
  приемлемы; дословный XML БКИ и так лежит в `bki_reports.raw_xml`.

### Маппинг `status` (рекомендация)
- **БКИ:** `КодРезультата` 0 → `ok`; 3 → `no_history`; 9 / таймаут / сетевой сбой →
  `unavailable`; прочее → `error`.
- **СтопЛист:** HTTP 200 → `ok`; таймаут/сбой → `unavailable`; иное → `error`.

## 5. Поток (sequence)

```mermaid
sequenceDiagram
    participant P as PetBank (клиент интеграций)
    participant S as Внешний сервис (БКИ / СтопЛист)
    participant J as Журнал external_service_calls
    P->>P: t0 = now(), сформировать запрос
    P->>S: HTTP-запрос (XML для БКИ / GET для СтопЛиста)
    S-->>P: Ответ (XML / JSON) либо таймаут/ошибка
    P->>P: привести запрос+ответ к JSON; status, http_status, latency_ms
    P->>J: save_external_call(service, application_id, payload, …)
    J-->>P: id записи
    Note over P,J: bki_reports (для БКИ) пишется рядом — не меняется
```

## 6. Repository API

```python
async def save_external_call(
    session: AsyncSession,
    *,
    service: str,
    application_id: uuid.UUID | None,
    request: dict | None,
    response: dict | None,
    status: str | None = None,
    http_status: int | None = None,
    latency_ms: int | None = None,
) -> int:
    """Записать один вызов внешнего сервиса в журнал. Возвращает id строки."""
```

`payload` собирается внутри функции как `{"request": request, "response": response}`.

## 7. Границы объёма

**Входит в эту итерацию:**
- ORM-модель `ExternalServiceCall` в `models.py`.
- Миграция `0006_external_service_calls` (down_revision = `0005_bki_reports`), аддитивная.
- Хелпер `xml_to_dict(...)` в `bki_parse.py` (там уже разбор XML БКИ).
- Функция `repository.save_external_call(...)`.
- Юнит-тесты (см. §8).

**НЕ входит сейчас** (отдельный следующий шаг, чтобы не трогать горячий путь заявки):
- Подключение записи в боевые клиенты `bki.py` и `black_list.py`.
- GIN-индекс и запросы-выборки по содержимому `payload`.
- Ручка выгрузки/просмотра журнала.

## 8. Тест-план (юниты, SQLite)

- `save_external_call` вставляет строку и возвращает `id`; поля читаются обратно.
- Два вызова по одной заявке → **две** разные строки (append-only).
- `application_id = None` — вставка проходит (nullable).
- `payload` сохраняется и десериализуется как словарь (variant JSON на SQLite).
- `xml_to_dict`: XML ответа БКИ → ожидаемый словарь (теги/атрибуты/повторы-в-список).

## 9. Миграция и деплой

- Alembic `0006_external_service_calls`, линейно после `0005`.
- Аддитивная (новая таблица) → безопасна; накатывается автоматически в пайплайне
  деплоя (`alembic upgrade` перед `deploy`), ручной `migrate.yml` не нужен.

## 10. Соотношение с `bki_reports`

`bki_reports` не меняется: остаётся источником фич для скоринга и дословного XML.
`external_service_calls` — параллельный универсальный журнал сырых (приведённых к JSON)
запросов/ответов всех внешних сервисов. Дублирование данных по БКИ осознанное:
у таблиц разные задачи (скоринг vs аудит).
