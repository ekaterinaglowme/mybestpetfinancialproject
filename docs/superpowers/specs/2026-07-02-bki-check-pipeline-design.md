# Спека: пайплайн проверок в POST /applications/v2 — БКИ → чёрный список → внутренняя БД

Дата: 2026-07-02. Статус: одобрена пользователем (брейншторм в сессии).

## Зачем

Фундамент будущей скоринговой системы. Заявка проходит три проверки в заданном
порядке, данные бюро сохраняются рядом с заявкой **в момент решения** — это
исключает утечку данных (data leakage) при последующем обучении скоркарты:
фичи в датасете ровно те, что были известны при выдаче.

Порядок «дорогой БКИ первым» выбран осознанно: сейчас фаза сбора данных, отчёт
бюро нужен по **каждой** заявке (и по отклонённым тоже — иначе не посчитать
IV/WOE по полной популяции). Когда скоркарта заработает, порядок перевернётся
на «дёшево → дорого» (флага/переключателя сейчас не делаем — YAGNI).

## Поток ручки

```
POST /applications/v2
  ДО транзакции (внешние вызовы не держат соединение из пула — текущий паттерн):
  1) БКИ:  паспорт «1234567890» → Серия=[:4], Номер=[4:] → XML windows-1251
           → POST {BKI_URL}/report → разбор ответа в фичи
           сбой → лог + пауза BKI_RETRY_DELAY_SECONDS → одна повторная попытка
                → снова сбой → status=unavailable, фичи пустые (fail-open)
  2) ЧС:   check_passport — без изменений (fail-closed, как сейчас)

  В транзакции:
  3) get_or_create_user → флаги по своей базе (get_user_loan_flags):
       есть заём со status='выдано'      → причина «активный заём уже есть»
       есть заём со status='не вернули'  → причина «прошлый невозврат»
  4) make_decision_v2 (расширенная): возраст + ЧС + стоп-правило БКИ + внутренние флаги.
     Причины отказа аккумулируются ВСЕ (цепочка не рвётся на первой — фичи и
     полный список причин нужны по каждой заявке).
  5) Сохранение: application + bki_report (ВСЕГДА, в т.ч. для отклонённых)
     + loan (если approved и есть сумма — как сейчас).
```

## Правила решения (новые, поверх существующих «возраст ≥ 18» и ЧС)

| Правило | Условие | Текст причины | Лейбл метрики |
|---|---|---|---|
| Стоп-БКИ | договор с `Состояние Код ∈ {59, 52}` И `ПросроченнаяЗадолженность > 0` | «Текущая просрочка или списание в кредитной истории» | `bki_delinquency` |
| Активный заём | у пользователя есть заём `выдано` | «Активный заём уже есть» | `active_loan` |
| Прошлый невозврат | у пользователя есть заём `не вернули` | «Прошлый невозврат» | `prior_default` |

- `КодРезультата=3` (нет истории) — НЕ отказ: `status=no_history`, фичи NULL.
- Недоступность БКИ — НЕ отказ и НЕ причина в `reasons` (решение не меняет);
  след остаётся в `bki_reports.status='unavailable'` и логах. Fail-open —
  осознанный выбор: БКИ — риск-инструмент, не комплаенс (ЧС остаётся fail-closed).

## Протокол БКИ (регламент АО «КредБюро», ред. 2.4; выписка у пользователя в ~/Downloads/reglament-2021.md)

- `POST {BKI_URL}/report`, тело XML в **windows-1251**, `Content-Type: application/xml`.
- Запрос: `<Запрос><Партнер Код="PETBANK"/><Субъект><Паспорт Серия="…" Номер="…"/></Субъект></Запрос>`.
- Ответ: сперва `Служебная/КодРезультата`: `0`=отчёт есть, `3`=истории нет,
  `9`=сервис временно недоступен (**приходит с HTTP 200** → трактуем как сбой с ретраем).
- Суммы в ответе — в **копейках**; даты `ДД.ММ.ГГГГ`, пустая — «-».
- `ПлтСтрока`: `1`=вовремя, `A`=1–29 дн, `2`–`5`=30+…120+, `9`=безнадёжный/списание,
  `X`/`0`=нет данных. Ранг для `max_dpd`: `1→0, A→1, 2→2, 3→3, 4→4, 5→5, 9→6`;
  `X`/`0` в ранжировании пропускаются.
- HTTP 403 = неверный код партнёра → конфиг-инцидент: error-лог + ветка `unavailable`.
- SLA бюро: до 3 с, в пики до 15 с → таймаут и ретрай обязательны.

## Новые модули

### `app/src/bki.py` — клиент (по образцу `black_list.py`)

- `configure(client=None)` / `dispose()`; один `httpx.AsyncClient` на приложение,
  поднимается в lifespan (тесты инжектят свой).
- env: `BKI_URL` (дефолт `http://212.147.238.3:8091`), `BKI_TIMEOUT_SECONDS=3.0`,
  `BKI_RETRY_DELAY_SECONDS=10` (в тестах `0`), `BKI_PARTNER_CODE=PETBANK`.
- `get_report(passport) -> BkiReport` — один вызов+разбор; сбой → `BkiError`.
- `get_report_with_retry(passport) -> BkiReport | None` — обёртка: одна пауза
  `asyncio.sleep(BKI_RETRY_DELAY_SECONDS)` и вторая попытка; `None` = unavailable.
- Метрика `EXTERNAL_CALL_SECONDS{service="bki"}` (лейбл к существующей метрике).

### `app/src/bki_parse.py` — чистые функции без IO (как `loans.py`)

- `build_request_xml(passport: str, partner_code: str) -> bytes` — XML в windows-1251.
- `parse_report(raw: bytes) -> ParsedBki` — dataclass:
  `result_code`, `score`, `n_contracts`, `has_writeoff` (есть договор 52/59),
  `has_current_delinquency` (стоп-правило: 52/59 И просрочка>0),
  `overdue_amount_kop`, `max_dpd`, `n_late` (символы ≠ `1`, без `X`/`0`),
  `debt_load_kop` (Σ обязательств активных договоров), `inq_30`, `inq_90`, `inq_365`.
- `КодРезультата=9` → исключение `BkiRetryable` (клиент ретраит).
- Битый XML / не-XML / неизвестная кодировка → `BkiParseError` (ветка unavailable).

### Таблица `bki_reports` (миграция `0005_bki_reports`)

| Колонка | Тип | Примечание |
|---|---|---|
| `application_id` | Uuid PK, FK → applications | 1:1 с заявкой |
| `fetched_at` | DateTime(tz) | момент запроса в бюро |
| `status` | String, CHECK ∈ {`ok`,`no_history`,`unavailable`} | итог обращения |
| `score` | Integer, nullable | балл бюро (SCR-11) |
| `n_contracts` | Integer, nullable | |
| `has_writeoff` | Boolean, nullable | договор 52/59 в истории |
| `overdue_amount_kop` | BigInteger, nullable | суммы храним в копейках, как отдаёт бюро |
| `max_dpd` | Integer, nullable | ранг худшего символа ПлтСтроки |
| `n_late` | Integer, nullable | |
| `debt_load_kop` | BigInteger, nullable | |
| `inq_30` / `inq_90` / `inq_365` | Integer, nullable | запросы в бюро |
| `raw_xml` | Text, nullable | сырой ответ бюро — юридический след + переразбор |

При `status='unavailable'` фичи NULL; если от бюро был получен хоть какой-то
ответ (битый XML, `КодРезультата=9`) — он сохраняется в `raw_xml` для отладки,
при чистом таймауте/сетевой ошибке `raw_xml` = NULL. При `no_history` — фичи
NULL, `raw_xml` сохранён.

### `repository.py`

- `save_bki_report(session, …)` — вставка в той же транзакции, после `save_application`.
- `get_user_loan_flags(session, user_id) -> (has_active: bool, has_default: bool)` —
  один запрос по join loans→applications по `user_id`.

### `make_decision_v2` — расширение сигнатуры

Новые keyword-параметры: `bki: ParsedBki | None` (None = unavailable/не запрашивали),
`has_active_loan: bool`, `has_prior_default: bool`. Вызов переезжает внутрь
транзакции (после `get_or_create_user` — флаги требуют `user_id`); внешние
вызовы остаются до транзакции.

## Наружный контракт

- Ответ ручки НЕ меняется: те же 200 + `status`/`reasons`/… Новые тексты причин — см. таблицу правил.
- Латентность: happy path +SLA бюро (до ~3 с); worst case при лежащем бюро
  ≈ `2×BKI_TIMEOUT + BKI_RETRY_DELAY` ≈ 16 с. Осознанный трейд-оф до появления
  очереди (роадмап S3); глобального request-timeout на main нет.

## Метрики

- `EXTERNAL_CALL_SECONDS{service="bki"}` — латентность бюро.
- Новый counter `BKI_RESULT{status="ok|no_history|unavailable"}` — доля сбоев видна в Grafana.
- `REJECTION_REASONS` — новые лейблы: `bki_delinquency`, `active_loan`, `prior_default`.

## Тесты

- **Юниты `bki_parse`**: оба примера из регламента (Код=0 → все фичи, Код=3),
  Код=9 → `BkiRetryable`, битый XML → `BkiParseError`, ранжирование ПлтСтроки,
  копейки/даты с «-».
- **Юниты решения**: матрица — стоп-БКИ / активный заём / прошлый невозврат /
  fail-open (bki=None) / комбинации с возрастом и ЧС (причины суммируются).
- **Интеграционные (tests/)**: мок httpx-клиента БКИ (инжект как у ЧС) —
  одобрение с записью bki_report; отказ по стоп-правилу; unavailable → решение
  без БКИ + запись `unavailable`; ретрай после первого сбоя (delay=0).
- **Blackbox (tests_blackbox/)**: `bki_mock.py` (stdlib, по образцу
  `blacklist_mock.py`; детерминированные паспорта: с чистой историей / без
  истории / со списанием / «тормозит») в docker-compose обоих стендов;
  сценарии user story: отказ по просрочке в БКИ; бюро лежит → заявка одобрена
  (fail-open); отказ по своему прошлому невозврату. Формат — как в существующих
  blackbox-тестах: сначала русское описание user story, потом код; проверяем
  контракт и интеграцию, не бизнес-константы.
