# Статус займа для аналитики

Дата: 2026-06-30

## Проблема и зачем

Сейчас статус погашения займа **вычисляется на лету** из `repaid_at` (`NULL` →
«не отдал», дата → «отдал»), см. `loan_view` в `app/src/loans.py`. Для аналитики
нужно, чтобы статус **физически лежал колонкой в таблице `loans`** — чтобы
считать прямо в SQL (`SELECT status, COUNT(*) FROM loans GROUP BY status`), не
вычисляя его из других полей.

Кроме того, бинарный «вернул / не вернул» не выражает нужный жизненный цикл: без
понятия срока «только что выдано» и «не вернул деньги» неотличимы (оба —
`repaid_at IS NULL`). Срок вводить не хотим (сознательное решение). Поэтому
«не вернули» становится **явным исходом**, который фиксирует оператор, а не
вывод по времени.

## Модель статуса (4 значения, хранится в БД)

| Значение     | Смысл                                                        | Кто ставит |
|--------------|-------------------------------------------------------------|------------|
| `выдано`     | Заём выдан, исход ещё не зафиксирован                        | По умолчанию при выдаче |
| `вернули`    | Деньги вернули; `repaid_at` заполнен                         | Оператор через `repay` |
| `не вернули` | Денег не вернули (списание/невозврат); `repaid_at` остаётся `NULL` | Оператор через `repay` |
| `ошибка`     | Техническая ошибка обработки `repay` (БД доступна)           | Система автоматически |

## Машина состояний

```
create_loan ───────────────────────────► выдано        (server_default)

выдано ──repay(outcome=вернули)─────────► вернули    + repaid_at = <дата возврата>
выдано ──repay(outcome=не вернули)──────► не вернули    (repaid_at = NULL)
выдано ──сбой обработки repay (исключение)─► ошибка    (best-effort, ставит система)
```

- `выдано` — единственное «незакрытое» состояние.
- Закрыть заём (`repay`) можно только из статуса `выдано`. Повторный `repay` на
  уже закрытом (`вернули` / `не вернули` / `ошибка`) → `409`. Проверяем по
  **статусу**, а не по `repaid_at` (раньше — по `repaid_at`).
- `ошибка` оператором не передаётся — это системный исход.

## Изменение схемы

**Колонка** в таблице `loans`:

```
status  VARCHAR  NOT NULL  DEFAULT 'выдано'
CHECK (status IN ('выдано', 'вернули', 'не вернули', 'ошибка'))
```

- Тип — обычный `VARCHAR` с `CHECK` (а не Postgres `ENUM`): портативно для
  SQLite-тестов, не мешает будущим миграциям alembic.
- Хранимая колонка, **не** `GENERATED` — значение пишет приложение (4 состояния
  из одного `repaid_at` не выводятся).

**Два места правки схемы (тесты и прод идут разными путями):**

1. **Модель `Loan`** (`app/src/models.py`) — добавить поле `status` с
   `default="выдано"` (Python-уровень, ORM-объект всегда со статусом) и
   `server_default="выдано"` (DDL). Тесты строят схему из моделей
   (`Base.metadata.create_all` на SQLite, см. `tests/conftest.py`), поэтому без
   правки модели тесты колонку не увидят. `create_loan` при этом **не меняется** —
   дефолт проставляется сам.
2. **Миграция `alembic/versions/0004_loan_status.py`** — для прода (Postgres).
   - `add_column` со `server_default='выдано'` и `CHECK`-ограничением;
   - **бэкфилл существующих строк:** `UPDATE loans SET status = CASE WHEN
     repaid_at IS NOT NULL THEN 'вернули' ELSE 'выдано' END`;
   - `downgrade` — `drop_column`.

## Контракт ручки `POST /loans/{id}/repay`

Сейчас ручка жёстко значит «вернул» и прибивает `repaid_at = сегодня`. Делаем её
«зафиксировать исход».

**Тело запроса** (новая Pydantic-модель, например `RepayRequest`):

```json
{
  "outcome": "вернули" | "не вернули",   // по умолчанию "вернули"
  "repaid_at": "2026-06-20"              // опционально, только для "вернули"
}
```

**Логика:**

- `outcome = "вернули"`:
  - `repaid_at` опционально; если не передан — `сегодня` (сохраняет старое
    поведение «дёрнул repay без тела = вернул сегодня»);
  - **валидация диапазона:** `issued_at ≤ repaid_at ≤ сегодня`. Раньше выдачи
    вернуть нельзя; будущей датой зафиксировать возврат нельзя. Нарушение → `422`.
    Проверка — **в ручке** (а не в Pydantic-модели): `issued_at` известен только
    после загрузки займа из БД, модель тела его не знает.
  - ставит `status = 'вернули'`, `repaid_at = <дата>`.
- `outcome = "не вернули"`:
  - `repaid_at` неприменим; если передан → `422`;
  - ставит `status = 'не вернули'`, `repaid_at` остаётся `NULL`.
- Заём не в статусе `выдано` → `409` (уже закрыт).
- Заём не найден → `404` (как сейчас).
- `outcome = "ошибка"` от клиента не принимается (только `вернули` / `не вернули`
  в `Literal`) → `422`.

## Изменения `loan_view`

Статус теперь **хранится**, поэтому `loan_view` (`app/src/loans.py`) перестаёт его
вычислять и **принимает `status` аргументом**, прокидывая в ответ. Расчёт
`days_elapsed` / `current_rate` / `amount_owed` по `repaid_at` остаётся прежним.

- Сигнатура: добавить параметр `status: str`.
- Поле ответа `"status"` = переданный `status` (вместо `"отдал" if repaid_at`).
- Оба вызова в `app/src/server.py` (`get_loan_status`, `repay_loan`) передают
  `loan.status`.
- Pydantic-модель `LoanStatus` — обновить комментарий к полю `status`.

Примечание про долг при `не вернули`: `repaid_at` пуст → `amount_owed` считается
на сегодня и продолжает «расти». Для аналитики «вернул / не вернул» это неважно
(смотрим на `status`). Заморозка суммы на момент списания — вне скоупа (см. ниже).

## Обработка `ошибка`

Если обработка `repay` падает с исключением (например, `SQLAlchemyError`), система
**best-effort** ставит `status = 'ошибка'` отдельной записью (БД должна быть
доступна) и возвращает `500`. Полный отказ БД по определению себя не зафиксирует —
это принятое ограничение, а не баг.

## Вне скоупа (YAGNI)

- **Срок / дедлайн / авто-просрочка** — сознательно не вводим.
- **`closed_at`** для заморозки долга у `не вернули` — позже, если понадобится.
- **Статус ошибки на уровне заявки** — уже покрыт: сбой чёрного списка делает
  заявку `declined` (fail-closed), заём не создаётся.
