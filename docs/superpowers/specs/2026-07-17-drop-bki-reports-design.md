# Удаление `bki_reports` с сохранением фич в витрину — дизайн

- **Дата:** 2026-07-17
- **Статус:** дизайн согласован (Екатерина, 2026-07-17)
- **Автор:** Екатерина (+ Claude)
- **Связан с:** [партиционирование ради retention](2026-07-15-partitioning-retention-design.md) —
  эта работа **разблокирует** переезд `applications` (освобождает место под копию).

## 1. Зачем (бизнес-цель)

База `petbank` на VM подходит к квоте (**11.9 / 15 GiB, 79%**, рост ~1.5 GiB/день). Самый
тяжёлый объект — таблица `bki_reports` (**5.68 GiB, почти весь вес — колонка `raw_xml`** с сырым
ответом бюро).

Скоринговые фичи из БКИ аналитике возврата нужны **постоянно**, а сырой XML — **нет**: фичи уже
разобраны парсером `bki_parse.py`, а сам парсер валидирован кросс-проверкой (2026-07-16/17: поля
парсера сходятся с сырьём из JSONB журнала `external_service_calls`, вплоть до точных совпадений).

Решение: снять компактную **витрину `bki_features`** (все колонки, кроме `raw_xml`) → затем
**удалить `bki_reports`** целиком. Возврат диска **~5.7 GiB** (79% → ~41%), и это **разблокирует**
переезд `applications` на партиционирование (ему нужно место под копию — см. связанную спеку).

`raw_xml` удаляется **безвозвратно, без бэкапа** (осознанное решение): фичи сохранены, парсер
валидирован, требований хранить сырьё нет; дамп 5.68 GiB на саму VM не помещается (квота).

## 2. Scope

**В scope:**
- Витрина `bki_features` (миграция `0007_bki_features` — **уже написана** в ветке
  `feat/bki-features-vitrina`, всего 2 файла сверх `main`).
- Миграция `0008_drop_bki_reports` — `DROP TABLE bki_reports`.
- Чистка осиротевшего кода записи в `bki_reports` (§4).

**Вне scope:**
- Партиционирование (`external_service_calls` → `loans` → `applications`) — отдельные спека/планы.
- Живой БКИ-код (`bki.py`, `bki_parse.py`, `collect_bki_report`) — используется, не трогаем. Сбор
  БКИ идёт в журнал `external_service_calls` (`service='bki'`), а **не** в `bki_reports`.

## 3. Ключевые решения

1. **Два деплоя с ручным gate между ними.** Нельзя создавать витрину и дропать источник в одном
   деплое: битая копия + уже снесённый источник = потеря данных. Порядок: PR #1 (витрина) →
   проверка на проде → PR #2 (drop). Alembic-цепочка (`0008.down_revision = 0007_bki_features`)
   **дополнительно форсит** порядок — `0008` не накатится без `0007`.
2. **`raw_xml` без бэкапа** (см. §1).
3. **Чистку осиротевшего кода — в PR #2** (схема и код меняются вместе; не оставляем ORM-модель,
   ссылающуюся на удалённую таблицу).
4. **`downgrade` у `0008` создаёт пустую структуру `bki_reports`** (как `0005.upgrade`) — цепочка
   Alembic формально обратима; данные не восстанавливаются (raw_xml удалён намеренно).
5. **Alembic линейно:** `0006` → `0007_bki_features` → `0008_drop_bki_reports`. Партиционирование
   пойдёт `0009+`. Ветвления ревизий нет.
6. **Прод деплоится автоматически при push в `main`** → `DROP` уедет на прод сразу после мёржа
   PR #2. Поэтому витрину проверяем на проде **до** мёржа PR #2 (при сомнении — мёрж в тихое окно).

## 4. Осиротевший код (удаляем в PR #2)

Запись БКИ переключена со спец-таблицы на журнал: `collect_bki_report` (`server.py`) зовёт
`save_external_call(service="bki", ...)`, а `save_bki_report` / `BkiReport` больше **никто не
вызывает** (подтверждено grep по `main`). Мёртвыми остаются:

- модель `BkiReport` — `app/src/models.py` (класс);
- функция `save_bki_report` + импорт `BkiReport` — `app/src/repository.py`;
- тест `tests/test_bki_repository.py` — целиком (проверяет только `save_bki_report`).

**Не трогаем:** `bki.py`, `bki_parse.py`, `test_bki_client.py`, `test_bki_parse.py` (живой
клиент/парсер БКИ). Чтений `bki_reports` в рантайме нет.

## 5. Механика

### Этап 1 — витрина на прод (PR #1)
1. Ветку `feat/bki-features-vitrina` обновить от `origin/main` (rebase), открыть PR, зелёный CI, мёрж.
2. Push в `main` → CI накатывает `0007_bki_features` → на проде появляется `bki_features`
   (CTAS всех фич без `raw_xml`, PK `application_id`).

### Этап 2 — gate (руками на проде; runbook)
- `count(*)` по `bki_features` и `bki_reports` — **совпадают**;
- по 3–5 `application_id` значения фич в витрине == в источнике;
- (опц.) размер витрины разумный (без `raw_xml` — небольшой).
- Провал любой проверки → **стоп**, разбираемся; `bki_reports` не трогаем.

### Этап 3 — удаление (PR #2)
1. Миграция `0008_drop_bki_reports`: `op.drop_table("bki_reports")` (снимает и FK на `applications`
   — подарок будущему партиционированию `applications`).
2. Чистка кода (§4).
3. Тесты (§6) зелёные.
4. PR, зелёный CI, мёрж → CI накатывает `0008` → `DROP` на проде.

### Этап 4 — проверка после
- `bki_reports` отсутствует; `bki_features` цела; размер базы упал ~5.7 GiB
  (`pg_database_size` / `df` на VM).

## 6. Тестирование (blackbox, «сценарий словами → код»)

1. **Витрина есть и содержит фичи.** После миграций `bki_features` существует; её колонки = фичи
   `bki_reports` без `raw_xml`.
2. **Источник удалён, витрина цела.** После `0008` таблицы `bki_reports` в каталоге нет;
   `bki_features` на месте.
3. **Приём заявок не задет.** `POST /applications/v2` работает; вызов БКИ пишется в журнал
   `external_service_calls`, не в `bki_reports`.
4. **Unit (SQLite):** после удаления модели `BkiReport` пакет `tests/` зелёный
   (`test_bki_repository.py` удалён вместе с кодом).

Сверка «count и значения фич совпадают» — **на проде руками** (этап 2): в тестовом стенде данных
нет, это операционный gate, не автотест.

## 7. Риски и обработка ошибок

- **Битая/неполная копия витрины** → закрыт ручным gate (этап 2) + Alembic-порядком (0008 после 0007).
- **`raw_xml` невосстановим** → осознанно (§1).
- **Автодеплой при мёрже** → витрину проверяем на проде **до** мёржа PR #2 (§3.6).
- **`bki_reports` не заморожена?** Предпосылка: запись идёт только в журнал. Подтверждено на `main`
  (`save_bki_report` не вызывается). Перед стартом этапа 1 — перепроверить grep'ом.
- **Откат:** `alembic downgrade -1` вернёт пустую структуру `bki_reports` (без данных). Полный
  откат данных невозможен — цена возврата места.
