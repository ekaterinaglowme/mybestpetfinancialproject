- [ ] Посмотреть [STATUS.md](STATUS.md) — что влито, что в работе, куда расти.

## ▶️ Запустить локально

- [ ] Python 3.10+ установлен (`python3 --version`).
- [ ] Создать и активировать venv: `python3 -m venv .venv && source .venv/bin/activate`.
- [ ] Поставить зависимости: `pip install -r requirements.txt`.
- [ ] Запустить: `python server.py` (или `python server.py 8080`).
- [ ] Проверить живость: `curl http://localhost:8000/health` → `{"status":"ok"}`.
- [ ] Открыть Swagger: `http://localhost:8000/docs`.

## ➕ Добавить или изменить бизнес-правило

Пример: изменить верхнюю границу возраста, добавить страну в стоп-лист или новое
правило отказа.

- [ ] Открыть `server.py`, найти блок констант (`MIN_AGE`, `MAX_AGE`,
      `BLOCKED_COUNTRIES`).
- [ ] **Изменение существующего правила** — поправить константу
      (напр. `MAX_AGE = 40`, или `BLOCKED_COUNTRIES = {"китай", "сша"}`).
- [ ] **Новое правило** — в `make_decision()` добавить проверку и при нарушении:
      `reasons.append("…понятная причина…")` (статус станет `declined`
      автоматически, раз `reasons` непуст).
- [ ] Если новое правило — отдельная категория отказа, добавить инкремент
      `REJECTION_REASONS.labels(reason="новая_категория").inc()` (см.
      [метрики](#-добавить-новую-метрику)).
- [ ] **Сначала тест** (TDD): добавить кейс в `tests/test_decision.py`
      (`make_decision` с данными, нарушающими правило → `declined`, причина в
      `reasons`). Запустить — убедиться, что падает.
- [ ] Реализовать правило. Запустить `pytest -q` — всё зелёное.
- [ ] Обновить текст справки, если правило видно снаружи: строка `"rule"` в
      `GET /`, print в `run()`, при необходимости [API.md](API.md) и `README.md`.
- [ ] Выкатить (см. [чек-лист релиза](#-сделать-изменение-и-выкатить-в-прод)).

## 🧩 Добавить новое поле заявки

Пример: добавить поле `income` (доход).

- [ ] В `server.py` → модель `ApplicationRequest`: добавить поле с типом и
      (если нужно) значением по умолчанию.
- [ ] Если поле требует проверки — добавить `@field_validator`.
- [ ] Обновить `model_config` → `json_schema_extra` → `example` (пример для Swagger).
- [ ] Если поле участвует в решении — использовать его в `make_decision()`.
- [ ] Если поле должно попасть в ответ — добавить в `ApplicantInfo`/
      `ApplicationDecision` и заполнить в `make_decision()`.
- [ ] Тесты: валидация нового поля в `tests/test_decision.py`; при влиянии на
      решение — кейсы в `make_decision`/`tests/test_http.py`.
- [ ] `pytest -q` — зелёное. Swagger (`/docs`) обновится **автоматически** из модели.
- [ ] (Опционально) синхронизировать `openapi.yaml`, `requests.http`, `README.md`
      — это legacy-артефакты, основной источник схемы теперь код.

## 🛣️ Добавить новый эндпоинт

- [ ] В `server.py` после `app = FastAPI(...)` добавить функцию-обработчик с
      декоратором (`@app.get(...)` / `@app.post(...)`).
- [ ] Для тела/ответа использовать Pydantic-модели (тогда Swagger подхватит схему).
- [ ] Добавить путь в справку `GET /` (список `endpoints`), если он публичный.
- [ ] Тест в `tests/test_http.py` через `TestClient` (код ответа + тело).
- [ ] Проверить, что эндпоинт виден в `/docs`. `pytest -q` — зелёное.

## 📊 Добавить новую метрику

- [ ] В `metrics.py` объявить метрику (`Counter`/`Histogram`/`Gauge`) с понятным
      именем `petbank_*` и **ограниченным** набором лейблов (следить за
      кардинальностью — не класть в лейблы сырой текст/идентификаторы).
- [ ] В `server.py` импортировать её и инкрементить/`observe` в нужном месте
      (обычно в `make_decision()`).
- [ ] Тест в `tests/test_metrics.py`: после действия `/metrics` содержит нужную
      строку/лейбл.
- [ ] `pytest -q` — зелёное. Проверить руками: `curl localhost:8000/metrics | grep petbank_`.

## 📦 Сделать изменение и выкатить в прод

Полный путь от идеи до прода.

- [ ] Обновиться от main: `git fetch origin && git rebase origin/main`.
- [ ] Создать ветку: `git checkout -b feat/<что-делаю>`.
- [ ] Внести изменения **с тестами** (по чек-листам выше). Локально `pytest -q` зелёное.
- [ ] (Желательно) собрать образ локально, чтобы убедиться, что Dockerfile цел:
      `docker build -t petbank:local .`.
- [ ] Закоммитить осмысленными коммитами, запушить ветку.
- [ ] Открыть PR в `main`. Дождаться, пока CI прогонит **тесты** и **сборку образа**
      (на PR деплоя нет — это безопасно).
- [ ] Проверить, что новые/старые файлы попадают в образ (если добавила новый
      `.py`-модуль — **дописать его в `COPY` в `Dockerfile`**, иначе на проде
      будет `ModuleNotFoundError`).
- [ ] Смёржить PR (rebase, без merge-коммита).
- [ ] После мёржа CI сам: тесты → сборка и публикация образа в ghcr → деплой на VM
      → health-check. Проследить, что workflow зелёный.
- [ ] Проверить прод: `curl http://<vm>:8000/health` и пару реальных заявок.

> Если добавляла зависимость — она в `requirements.txt`, и образ её поставит. Если
> добавляла новый модуль — он в `COPY` Dockerfile. Эти два пункта — самые частые
> причины «локально работает, на проде нет».

## 🐞 Дебаг проблемы на проде

- [ ] Контейнер жив? `docker ps` (ищем `petbank`, статус `Up`/`healthy`).
- [ ] Логи: `docker logs --tail 200 petbank`. Искать `level":"ERROR"`, трейсбэки
      (`exc_info`), отказы (`"status":"declined"`).
- [ ] Воспроизвести запрос и взять его `request_id` из ответа (заголовок
      `X-Request-ID`), затем `docker logs petbank | grep <request_id>` — увидишь
      все логи именно этого запроса (бизнес + access, с телом).
- [ ] Метрики: `curl localhost:8000/metrics | grep -E 'http_requests_total|petbank_'`
      — всплеск ошибок? рост отказов?
- [ ] Какая версия задеплоена: `curl -s localhost:8000/metrics | grep petbank_app_info`
      (там `version`/`commit`).
- [ ] Если виноват последний релиз — откатиться на предыдущий образ по тегу
      `sha-<коммит>`: `docker pull …:sha-<prev>` и `docker run …` (или
      зареверть коммит в `main` и дать CI выкатить заново).

## 🔒 Мини-аудит безопасности

Для учебного стенда часть пунктов осознанно «ок», но знать риски полезно.

- [ ] **ПДн в логах.** Тело заявки (ФИО, телефон, ДР) пишется в лог открытым
      текстом. Ограничить доступ к логам и срок хранения; при необходимости —
      маскировать поля в middleware.
- [ ] **Plaintext HTTP.** Сервис слушает `0.0.0.0:8000` без TLS. В проде —
      reverse-proxy (nginx) + сертификат.
- [ ] **`/metrics` без авторизации.** Так задумано (внутренний скрейп), но эндпоинт
      не должен торчать в открытый интернет — ограничить сетью/файрволом.
- [ ] **Группа `docker` = root.** Деплой-аккаунт фактически рутовый на VM. В проде
      — изолировать (rootless Docker / отдельный хост).
- [ ] **Секреты.** `SSH_KEY` и токены — только в GitHub Secrets, не в коде. `.env`
      — не коммитить (он в `.gitignore` и `.dockerignore`).
- [ ] **Branch protection.** Включить «Require status checks → Tests» на `main`,
      чтобы нельзя было смёржить с красными тестами.
